# Live answer evaluation

The normal PR and scheduled `Reading Companion library evaluation` runs two retrieval-only suites: 31 all-books questions and 6 selected-book questions spanning philosophy, science, history, literature, and religion. Both search the published index and verify source-page identity/fingerprints; they make **zero Cloudflare AI calls**. The selected-book suite also checks that retrieval stays inside the chosen book. It does not add cases to the metered live-AI benchmark.

The active live-answer and retrieval-only workflows now target the same release as `remote-library.mjs`: v49 data with `reader-fingerprints-v3/coverage-v3.json`. Both corpus and fingerprint preflights must match before retrieval or any live AI call. Historical run notes below retain the v47/v48 versions those artifacts actually used.

## Consolidated answer-quality benchmark

Use **Reading Companion answer quality benchmark** for one dispatch and one artifact. Choose `calibration` for God-is-love, simulation, and Buddha, or `acceptance` for the full frozen acceptance set. Calibration can run once or three interleaved attempts per question. `baseline` uses the current 24-candidate/four-book retrieval profile; `expanded` tests up to 48 candidates/six books while keeping the six-page final answer packet unchanged. Expanded retrieval is evaluation-only until its trace and quality results justify changing the public default.

Choose `compare-expansion` to run a paired Worker comparison with identical planner output and submitted pages: ordinary composition plus review, then composition plus a post-composition expansion call followed by the same review stage. The expansion can only use the already submitted verified passage windows and citations. It cannot recover a passage retrieval missed. Each expanded answer adds one Worker inference call. The paired comparison runs both answer variants, so it uses five answer-stage calls per question instead of the two-call ordinary path (three additional calls total). If expansion fails, the Worker retains the original draft and continues through the existing review stage. The optional search-gap planner remains conditional and may add one call when the retrieved text has weak local coverage; it already exists in the live path and is not duplicated by this workflow.

Choose `compare-selection` to compare the current deterministic selector with one model call that ranks pages from the same retrieved candidate pool before the six-page limit. The model sees bounded excerpts for up to 48 candidates and the question's parts; it can return only IDs from that pool. The normal page, byte, library-version, and fingerprint checks still apply. This mode runs both answer packets through the same compose-and-review path and records the candidate pool, selector decision, selected pages, usage, and each answer separately. A selector failure is clearly marked and falls back to the deterministic packet for trace collection; that attempt does not count as a successful model-selection comparison. A missing useful passage in the candidate pool remains a retrieval miss and is reported separately from a selection miss. This experiment is authenticated and evaluation-only: it does not change the public chatbot path. It adds one selector call and one extra compose/review answer (three additional Worker inference calls per question overall); the existing conditional gap planner may still add its usual call.

Use the `selectionVariants` section of the artifact to compare the deterministic and model-selected answer scores. Judge source relevance and answer quality from the candidate excerpts, both selected-page lists, cited passages, and the five human rubric dimensions. Do not treat a model's `supported` label, a structural pass, or a higher citation count as proof that evidence supports a claim. The selection experiment intentionally does not combine with post-composition expansion, so it isolates the effect of choosing pages.

The artifact records `structuralPassed` separately from `qualityStatus`. Each case also records `gapQueryPartLinks`, per-part `selectionCoverage`, and a bounded `selectionAudit` of the best candidates and selected pages for each question part. The audit shows local quoted-phrase and coherent-term-cluster signals, retrieval score, linkage, and selected state; it marks `semanticRelevanceScored: false`. In `compare-selection`, both the deterministic and model-selected packets receive the same audit. These fields help reviewers see whether a relevant-looking candidate was found and whether it reached the packet, but they do not prove semantic support or count as a quality pass.

Planner failures remain distinct from retrieval misses and answer failures. The compact `plannerFailure` field retains its established HTTP-status and failure-code shape for existing artifact readers; `plannerFailureDiagnostics` adds the initial planning stage and fixed failure class. `gapPlannerFailureDiagnostics` records the same safe details for the conditional planner while the legacy `gapPlannerFailure` string remains available. When gap planning fails, evaluation continues with the original verified retrieval packet and does not add a retry or query.

Structural misses do not fail this workflow's report-collection step; request failures still do. `qualityStatus` remains `pending-human-review` until the five dimensions are scored: accuracy, question coverage, explanation quality, citation support, and citation completeness. A green Actions run means the trace was collected, not that answer quality passed. Compare the before/after candidate sets, selection audits, selected pages, exact composer windows, answer prose, review decisions, and rubric scores. Word count and number of cited books are diagnostic measures, not quality gates.

`Reading Companion live answer evaluation` is a separate, manually dispatched workflow. It requires a live-AI confirmation checkbox. The `planner` mode is a low-cost, two-question check: it asks the live Worker planner for one selected-book plan and one All Books cross-work plan, then runs retrieval to see whether the expected books appear. It makes two planner inference calls and skips answer generation. It does not assess passage relevance or answer quality.

The default smoke run asks three questions: the 1 John 4:7–12 retrieval case, the Hawking black-hole case, and Aristotle on habituation. Choose `full` only when you want the complete 30-question benchmark; the full mode has a second confirmation checkbox. Runs are serialized and API requests are spaced at least 30 seconds apart to stay within the pilot's rate limits.

The `quality` mode defaults to the cases’ selected-book scope and uses two fixed, curated queries per case, so its seven questions spend calls on answer composition and review instead of planning. Its `plannerSkipped` field is true in that mode. Choose the quality scope `all-books` to run all seven questions without a selected-book restriction and use the live planner for each; this estimates 21 baseline inference calls (7 planner + 14 answer/review), plus conditional repairs. This is the mode to use when validating changes to planner query facets against the full seven-question set. A weak-coverage case may add one conditional gap-planner call; the artifact reports its maximum allowance separately from baseline inference calls. The report records `searchScope` and whether planning was skipped. Smoke costs roughly 9 inference calls and the full suite 90, before conditional repairs. This workflow is never attached to pull requests or a schedule.

Quality reports distinguish the candidate pool from the answer packet. In each `sourceGroups` entry, `candidateBookIds` and `candidateFound` say whether an expected work appeared in the hydrated `retrievalCandidates`; `selectedBookIds` and `selectedForComposition` say whether it was sent in `submittedSources`; `citedBookIds` and `cited` say whether the answer cited it. The older `retrievedBookIds`/`retrieved` fields remain as compatibility aliases for selection into the answer packet. For each requested part, `partEvidenceAudit` shows whether its evidence IDs resolve to the review map, cited source, and submitted page. `answerCoverageConsistent` checks that reported coverage matches the part statuses and flags explicit prose that denies a comparison marked supported. These are structural checks only. They cannot determine whether the cited passage semantically supports the claim or whether the interpretation is correct; inspect `answerText`, `evidenceMap`, highlights, and cited page text manually. The automated `passed` count is a review signal, not an AI truth grade.

## Workbench-breadth experiment

The live browser now searches up to 24 hydrated candidate pages across four books, then sends at most six pages to the Worker. For a one-part question, source selection can reserve up to three distinct linked works before filling the remaining six-page packet. The public-library evaluator uses the same facet expansion, ranking, hydration, candidate cap, and answer-source cap as the browser; fixed benchmark query plans keep retrieval runs reproducible while corpus and scope preflights remain live. The Worker's existing composer may use a second short paragraph when a different work adds relevant evidence or context; it stays concise when only one source answers or the pages are thin. The verified page identities, six-page request cap, claim review, citation checks, and model-call count remain unchanged.

Verified key passages now use semantic blockquotes with a subtle theme-aware background and left rule, keeping each excerpt visually separate while retaining its source attribution and existing Read passages control.

To review the change, run `acceptance-buddha-on-death` in All Books mode three times after the site and Worker PRs are merged and deployed. Compare the trace stages in order: `searches` → `candidates` → `submittedSources` → cited pages → reviewed claims. Score whether the primary answer is relevant, whether distinct works add useful support, whether source voices are attributed accurately, and whether the second paragraph adds explanation instead of padding. The automated required-source check only ensures that at least one Buddhist teaching text is represented; human review decides whether additional sources are relevant and whether the synthesis is supported. The local workbench defaults to v48 while the live site uses v49, so align the local corpus before treating a local/live replay as a controlled comparison.

Inline numbered citations and the source card’s “Read passages” button both open the in-page reader with verified excerpts highlighted when the text can be located. Inline citations use the exact reviewed quote for the cited answer claim and source. Resolve those links against the complete answer before Markdown rendering splits it into text nodes; if an exact claim link is missing or ambiguous, show no highlight rather than borrowing another claim’s quote. The source card may show multiple reviewed excerpts from that page.

## Acceptance calibration and repeatability

The All Books **acceptance** suite preserves its original seven questions and adds three approved calibration cases, in order: `acceptance-god-is-love`, “What does ‘God is love’ mean?”; `acceptance-simulation-hypothesis`, “Are we living in a simulation?”; and `acceptance-buddha-on-death`, “What did Buddha say about death?” The Bible is the required core source for the first case; Simone Weil may add a distinct, well-supported perspective but is optional. The simulation case tests directness and epistemic calibration; it requires evidence from Descartes on skeptical doubt and at least one of Berkeley or Hume on perception and reality, while keeping those arguments distinct from evidence for a computer simulation. The Buddha case tests broad retrieval and synthesis: prioritize Buddhist teaching texts that directly address death, and use a second relevant work when it adds something distinct. Clearly distinguish compiled texts and later interpretation from a verified verbatim historical statement by the Buddha.

The earlier **Reading Companion repeated calibration** workflow runs simulation and Buddha three times each. Use the consolidated benchmark above for new calibration because it also includes God-is-love and lets one run compare retrieval profiles and answer variants. Historical artifacts from the earlier workflow remain useful baselines; compare runtime revisions and corpus fingerprints before drawing conclusions.

The October 29 repeated calibration run #3 completed all six attempts without request failures, but only one passed structural checks. Its traces showed that none attempted conditional gap planning: page-wide token overlap let a passage about imitation count as coverage for the simulation question. Sentence/clause term matching was added, but run #4 exposed an index-entry false positive: separate entries in *Nicene and Post-Nicene Fathers* III placed “simulation” and “Christian living at Jerusalem” close together. The site now detects repeated page-reference lists, prevents those entries from counting as coherent coverage, and excludes index-like pages from the answer packet. When an index page is the strongest lexical match, the trace sends its bounded reason, matched terms, and page locator to the existing optional gap planner. The planner still may only return broad alternate searches and cannot prescribe authors or works. The same run showed differently sized *Teaching of Buddha* excerpts carrying the same Amida passage. Same-work deduplication now compares three-word-shingle containment against the shorter substantial passage without a page-length ratio, while retaining materially different wording. These diagnostics are not semantic relevance judgments; inspect `retrievalCoverage`, `gapQueries`, the before/after candidate set, submitted pages, and answer review. Case-specific source expectations remain in this evaluator only.

The simulation case is intentionally not a demand for a yes-or-no metaphysical verdict. A strong answer says that the cited sources do not establish whether we live in a simulation, then uses Descartes and Berkeley or Hume to explain the related epistemological question without treating those positions as proof. A theological use of “simulation,” or passages about hallucination, memory, or models of reality, may be mentioned only as limited analogies and must not be confused with the computational hypothesis. Review the answer text and its cited passages manually: a structural pass confirms source linkage and coverage labels, not the correctness of the synthesis.

When planning is unavailable and the workflow falls back to direct retrieval, the shared retriever searches the unchanged reader question within the existing book scope. It does not infer a canonical source or append topic-specific query terms. Artifacts record the actual queries under `searches`; acceptance cases may still require expected source groups as evaluation criteria, but those requirements do not modify live retrieval.

The question-steering audit removed topic-triggered search additions from shared runtime code: the “God is love” 1 John fallback, Kant-only causal-necessity vocabulary, and dependent-origination/dependent-arising phrase expansion. Query language now comes from the reader and the existing planner response. Generic safeguards remain for explicit work and verse scope, question-part coverage, source provenance, and evidence validation. A planner outage still uses direct retrieval and the configured scope; it does not invoke a second planner or alter the question. The full rationale and cross-repository boundary are in the book-chatbot [question-steering audit](https://github.com/jsynon/book-chatbot/blob/main/docs/question-steering-audit.md).

For each answer, score these dimensions independently from 0 (fail) to 2 (strong): accuracy, question coverage, explanation quality, citation support, and citation completeness. Record a short note for any score below 2 that names the claim or passage driving it. Keep those human scores separate from the automated supported/partial/unsupported labels; compare the two signals across cases to spot where the partial labels miss an incomplete answer or flag an answer that a reviewer considers complete.

## Recheck a saved quality report without AI or network calls

The standalone `recheck-live-answer-evaluation.mjs` script reapplies the current structural audit to a saved quality JSON report. It does not contact the Worker, retrieve books, or call a model. First extract `reading-companion-live-answer-evaluation.json` from the GitHub Actions artifact ZIP, then run:

```powershell
node .\reading-companion\recheck-live-answer-evaluation.mjs `
  --input .\downloaded-artifact\reading-companion-live-answer-evaluation.json `
  --output .\downloaded-artifact\reading-companion-live-answer-evaluation.offline-rechecked.json
```

The new `offlineRecheck` fields preserve the original report and show the corrected structural score alongside it. This can correct evaluator false negatives, but it does not change the generated answer or verify factual truth. Run its regression tests with `node --test .\reading-companion\live-answer-evaluation.test.mjs`.

## October 29, 2026: fuller answers and speaker attribution

The Worker review now records a per-source attribution status and attributed speaker for explicit named-speaker claims. When a passage contains a nearby quotation credit or footnote, inspect that context before deciding whether a claim such as “the Buddha taught…” is supported. A conflict or unclear attribution should lower citation support and accuracy even when the quoted words are located on the page. The source-level review trace records the review status, attributed speaker, and rejection reason.

The composer may use two or three paragraphs and roughly 160–260 words as a guide when relevant passages explain distinct facets, whether they come from one work or several. This is not a minimum. If one passage answers the question or the evidence is thin, a shorter answer can be better. Word count, number of cited works, and retrieval breadth are diagnostic signals, not additional scores; preserve the five established human scores: accuracy, question coverage, explanation quality, citation support, and citation completeness.

Broad reality and existence questions receive one generic epistemic context search lead only when planner queries omit that vocabulary. The question remains one coverage part and keeps its direct query. No author pair is hardcoded, no retrieval cap is raised, and no model call is added. Offline regressions cover this backstop and a quoted-speaker conflict.

After merge and deployment, rerun the simulation and Buddha workflows and inspect, in sequence, the search leads, retrieved candidates, submitted source pages, composer windows, reviewer attribution decisions, and final citations. Score the generated answers with the existing five-dimension rubric; compare length and distinct relevant works as diagnostics. The workflow's structural status alone does not establish answer quality.

When the composer explicitly says the supplied pages do not answer the question and no cited answer survives validation, the Worker records `model-reported-insufficient-evidence` and returns the existing structured insufficient-evidence outcome with no answer coverage. This is a successful classification of the evidence gap, not a successful answer and not a workflow quality pass. Malformed output and unrelated citation failures retain their existing failure classifications.
