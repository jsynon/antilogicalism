# Live answer evaluation

The normal PR and scheduled `Reading Companion library evaluation` runs two retrieval-only suites: 31 all-books questions and 6 selected-book questions spanning philosophy, science, history, literature, and religion. Both search the published index and verify source-page identity/fingerprints; they make **zero Cloudflare AI calls**. The selected-book suite also checks that retrieval stays inside the chosen book. It does not add cases to the metered live-AI benchmark.

The active live-answer and retrieval-only workflows now target the same release as `remote-library.mjs`: v49 data with `reader-fingerprints-v3/coverage-v3.json`. Both corpus and fingerprint preflights must match before retrieval or any live AI call. Historical run notes below retain the v47/v48 versions those artifacts actually used.

## Consolidated answer-quality benchmark

Use **Reading Companion answer quality benchmark** for one dispatch and one artifact. Choose `calibration` for the four targeted diagnostic cases, `single-case` to run one acceptance question, or `acceptance` for the full frozen set. For a Buddha-only run, choose `single-case`, keep the default `acceptance-buddha-on-death`, and choose `1` or `3` attempts. A single-case run costs only that case's answer calls per attempt; selecting three attempts does not run the other acceptance questions. Calibration can also run once or three interleaved attempts per question, while the full acceptance suite always runs once. `baseline` retrieves up to 32 pages across four books; `expanded` retrieves up to 48 pages across six books. Both pass the retrieved candidate pool to the Worker for semantic evidence selection after fingerprint verification. The final composer still receives at most six pages and 35 KB.

The live answer path now separates retrieval recall from answer-packet selection. A normal reviewed all-books question uses one planning call, one evidence-selection call, one composition call, and one review call. Selected-books requests may skip planning. Conditional gap planning may add one retrieval-only call if local text coverage is weak. Selection failures are marked and use a bounded retrieval-order fallback; review and deterministic citation checks still apply.

Choose `compare-selection` to compare a six-page candidate input against the full retrieved candidate pool while keeping the Worker selector, composer, and reviewer the same. This is a candidate-recall comparison, not a deterministic-versus-model selector comparison. It runs two answers per case, each with the same three answer-stage calls (selection, composition, review). Human-score both variants independently. The full-pool arm may contain up to 48 pages and is subject to the same request byte and fingerprint limits.

Choose `compare-expansion` to compare ordinary composition plus review with composition plus a post-composition expansion call followed by the same review. The expansion can use only already submitted, verified passages and cannot recover text retrieval missed. The paired comparison runs both answer variants. Do not combine expansion and candidate-pool comparison in the same run; first determine whether evidence selection improves, then assess expansion on a fixed selected packet.

The artifact records `structuralPassed` separately from `qualityStatus`. It now also records `answerCompleteness` separately from library `coverage`: answer completeness reflects whether the reviewed prose directly and coherently answers the question; coverage reflects how fully the answer is established by the selected library evidence. A complete answer can therefore retain useful, reviewed general context while clearly reporting partial library coverage. For each requested part, `answerStatus` and `status` preserve the same distinction. Offline rechecks retain both values and make no AI or network calls. Review the raw candidate set, Worker selection stage, selected pages, exact composition windows, answer prose, review decisions, and the five human rubric dimensions. Do not treat the model's `supported` label, a structural pass, a higher citation count, a word count, or source count as proof of quality. Source selection and human scoring answer different questions.

Planner failures remain distinct from retrieval misses and answer failures. The compact `plannerFailure` field retains its established HTTP-status and failure-code shape for existing artifact readers; `plannerFailureDiagnostics` adds the initial planning stage and fixed failure class. `gapPlannerFailureDiagnostics` records the same safe details for the conditional planner while the legacy `gapPlannerFailure` string remains available. When gap planning fails, evaluation continues with the original verified retrieval packet and does not add a retry or query.

The top-level `scopeSummary` groups result rows using each case's `evaluationScope` (with compatibility fallbacks for older `scope` records and selected-book IDs). In repeated runs, its `cases` count is the number of completed attempt rows in that scope; `repeatSummary` groups those attempts by question.

Structural misses do not fail this workflow's report-collection step; request failures still do. `qualityStatus` remains `pending-human-review` until the five dimensions are scored: accuracy, question coverage, explanation quality, citation support, and citation completeness. A green Actions run means the trace was collected, not that answer quality passed. Compare the before/after candidate sets, selection audits, selected pages, exact composer windows, answer prose, review decisions, and rubric scores. Word count and number of cited books are diagnostic measures, not quality gates.

Highlight quality is now scored separately in `highlightHumanReview` and summarized at report level under `highlightReview`; it uses the same five 0–2 dimensions as answer review, applied to excerpt fidelity, coverage, context, claim relevance, and completeness. Scores remain pending until a person fills them in. `quoteLocated` only confirms that text appears on the submitted page. Highlight-to-answer linkage uses the reviewer's claim point and cited source; ambiguous wording is marked unresolved instead of inheriting every sentence that cites that page. Adjacent excerpts can be merged for display only when they are verified contiguous ranges for the same claim and part.

`Reading Companion live answer evaluation` is a separate, manually dispatched workflow. It requires a live-AI confirmation checkbox. The `planner` mode is a low-cost, two-question check: it asks the live Worker planner for one selected-book plan and one All Books cross-work plan, then runs retrieval to see whether the expected books appear. It makes two planner inference calls and skips answer generation. It does not assess passage relevance or answer quality.

The default smoke run asks three questions: the 1 John 4:7–12 retrieval case, the Hawking black-hole case, and Aristotle on habituation. Choose `full` only when you want the complete 30-question benchmark; the full mode has a second confirmation checkbox. Runs are serialized and API requests are spaced at least 30 seconds apart to stay within the pilot's rate limits.

The `quality` mode defaults to the cases’ selected-book scope and uses two fixed, curated queries per case, so its seven questions spend calls on answer composition and review instead of planning. Its `plannerSkipped` field is true in that mode. Choose the quality scope `all-books` to run all seven questions without a selected-book restriction and use the live planner for each; this estimates 21 baseline inference calls (7 planner + 14 answer/review), plus conditional repairs. This is the mode to use when validating changes to planner query facets against the full seven-question set. A weak-coverage case may add one conditional gap-planner call; the artifact reports its maximum allowance separately from baseline inference calls. The report records `searchScope` and whether planning was skipped. Smoke costs roughly 9 inference calls and the full suite 90, before conditional repairs. This workflow is never attached to pull requests or a schedule.

Quality reports distinguish the candidate pool from the answer packet. In each `sourceGroups` entry, `candidateBookIds` and `candidateFound` say whether an expected work appeared in the hydrated `retrievalCandidates`; `selectedBookIds` and `selectedForComposition` say whether it was sent in `submittedSources`; `citedBookIds` and `cited` say whether the answer cited it. The older `retrievedBookIds`/`retrieved` fields remain as compatibility aliases for selection into the answer packet. For each requested part, `partEvidenceAudit` shows whether its evidence IDs resolve to the review map, cited source, and submitted page. `answerCoverageConsistent` checks that reported library coverage matches the part evidence statuses and flags explicit prose that denies a comparison marked supported. `structuralPassed` requires complete answer status plus citation, evidence-link, source-group, and contract integrity; it no longer fails solely because `coverage` is partial. These are structural checks only. They cannot determine whether the cited passage semantically supports the claim or whether the interpretation is correct; inspect `answerText`, `evidenceMap`, highlights, and cited page text manually. The automated `passed` count is a review signal, not an AI truth grade.

## Workbench-breadth experiment

The live browser now searches up to 32 hydrated candidate pages across four books, then sends at most six pages to the Worker. For a one-part question, source selection can reserve up to three distinct linked works before filling the remaining six-page packet. The public-library evaluator uses the same facet expansion, ranking, hydration, candidate cap, and answer-source cap as the browser; fixed benchmark query plans keep retrieval runs reproducible while corpus and scope preflights remain live. The Worker's existing composer may use a second short paragraph when a different work adds relevant evidence or context; it stays concise when only one source answers or the pages are thin. The verified page identities, six-page request cap, claim review, citation checks, and model-call count remain unchanged.

Verified key passages now use semantic blockquotes with a subtle theme-aware background and left rule, keeping each excerpt visually separate while retaining its source attribution and existing Read passages control.

To review the change, run `acceptance-buddha-on-death` in All Books mode three times after the site and Worker PRs are merged and deployed. Compare the trace stages in order: `searches` → `candidates` → `submittedSources` → cited pages → reviewed claims. Score whether the primary answer is relevant, whether distinct works add useful support, whether source voices are attributed accurately, and whether the second paragraph adds explanation instead of padding. The automated required-source check only ensures that at least one Buddhist teaching text is represented; human review decides whether additional sources are relevant and whether the synthesis is supported. The local workbench defaults to v48 while the live site uses v49, so align the local corpus before treating a local/live replay as a controlled comparison.

Inline numbered citations in the answer open the in-page reader with verified excerpts highlighted when the text can be located. In each key-passage card, the non-clickable citation label, linked book title, and any pseudonym or editorial attribution appear together before the excerpts. “Read passages” remains the card’s reader control; the book-title link opens the original scanned book. Inline answer citations use the exact reviewed quote for that answer claim and source. Resolve those links against the complete answer before Markdown rendering splits it into text nodes; if an exact claim link is missing or ambiguous, show no highlight rather than borrowing another claim’s quote. The source card may show multiple reviewed excerpts from that page.

## Acceptance calibration and repeatability

The All Books **acceptance** suite preserves its original seven questions and adds four approved calibration cases, in order: `acceptance-god-is-love`, “What does ‘God is love’ mean?”; `acceptance-simulation-hypothesis`, “Are we living in a simulation?”; `acceptance-buddha-on-death`, “What did Buddha say about death?”; and `acceptance-life-meaning-authors`, “How do different authors in the library approach the question of life's meaning?” The Bible is the required core source for the first case; Simone Weil may add a distinct, well-supported perspective but is optional. The simulation case tests directness and epistemic calibration without prescribed authors, schools, search queries, or required source groups. Review whether the answer distinguishes a general skeptical possibility from evidence for a computational simulation, and whether cited passages genuinely clarify the question. The Buddha case tests broad retrieval and synthesis: prioritize Buddhist teaching texts that directly address death, and use a second relevant work when it adds something distinct. Clearly distinguish compiled texts and later interpretation from a verified verbatim historical statement by the Buddha. The life-meaning case is a broad All Books diagnostic with no prescribed authors, books, search terms, or required source groups; review whether retrieved authors directly address meaning and whether the answer synthesizes their distinct approaches instead of listing adjacent topics.

The earlier **Reading Companion repeated calibration** workflow runs simulation and Buddha three times each. Use the consolidated benchmark above for new calibration because it also includes God-is-love and lets one run compare retrieval profiles and answer variants. Historical artifacts from the earlier workflow remain useful baselines; compare runtime revisions and corpus fingerprints before drawing conclusions.

The October 29 repeated calibration run #3 completed all six attempts without request failures, but only one passed structural checks. Its traces showed that none attempted conditional gap planning: page-wide token overlap let a passage about imitation count as coverage for the simulation question. Sentence/clause term matching was added, but run #4 exposed an index-entry false positive: separate entries in *Nicene and Post-Nicene Fathers* III placed “simulation” and “Christian living at Jerusalem” close together. The site now detects repeated page-reference lists, prevents those entries from counting as coherent coverage, and excludes index-like pages from the answer packet. When an index page is the strongest lexical match, the trace sends its bounded reason, matched terms, and page locator to the existing optional gap planner. The planner still may only return broad alternate searches and cannot prescribe authors or works. The same run showed differently sized *Teaching of Buddha* excerpts carrying the same Amida passage. Same-work deduplication now compares three-word-shingle containment against the shorter substantial passage without a page-length ratio, while retaining materially different wording. These diagnostics are not semantic relevance judgments; inspect `retrievalCoverage`, `gapQueries`, the before/after candidate set, submitted pages, and answer review. Case-specific source expectations remain in this evaluator only.

The simulation case is intentionally not a demand for a yes-or-no metaphysical verdict. A strong answer addresses the question, distinguishes a general skeptical possibility from evidence for a computational simulation, and explains the limits of what the cited passages establish. Any philosophical analogy should be tied to the question and clearly distinguished from evidence that the world is computationally simulated. Review the answer text and its cited passages manually: a structural pass confirms source linkage and coverage labels, not the correctness of the synthesis.

When planning is unavailable and the workflow falls back to direct retrieval, the shared retriever searches the unchanged reader question within the existing book scope. It does not infer a canonical source or append topic-specific query terms. Artifacts record the actual queries under `searches`; acceptance cases may still require expected source groups as evaluation criteria, but those requirements do not modify live retrieval.

The question-steering audit removed topic-triggered search additions from shared runtime code: the “God is love” 1 John fallback, Kant-only causal-necessity vocabulary, and dependent-origination/dependent-arising phrase expansion. Query language now comes from the reader and the existing planner response. Generic safeguards remain for explicit work and verse scope, question-part coverage, source provenance, and evidence validation. A planner outage still uses direct retrieval and the configured scope; it does not invoke a second planner or alter the question. The full rationale and cross-repository boundary are in the book-chatbot [question-steering audit](https://github.com/jsynon/book-chatbot/blob/main/docs/question-steering-audit.md).

For each answer, score these dimensions independently from 0 (fail) to 2 (strong): accuracy, question coverage, explanation quality, citation support, and citation completeness. Record a short note for any score below 2 that names the claim or passage driving it. Keep those human scores separate from the automated supported/partial/unsupported labels; compare the two signals across cases to spot where the partial labels miss an incomplete answer or flag an answer that a reviewer considers complete.

The reviewed baseline for workflow run [#41164688565](https://github.com/jsynon/antilogicalism/actions/runs/41164688565) is saved at `benchmarks/human-reviews/quality-run-41164688565.json`. It records the 12 assistant-scored answers, notes, structural result, reviewer part/claim labels, and review support issues without changing the original Actions artifact. The score was 88/120 (7.33/10); all 12 passed structural checks and all 12 reviewer part decisions were `answered`, even though the answer scores and claim decisions show important differences. This is a calibration reference, not a release threshold or independent double score.

New benchmark artifacts summarize reviewer part labels, validated part labels, claim labels, review-contract completeness, and support-issue counts separately from `structuralPassed` and `humanReview`. The live Worker response calls its trace `trace`; the saved case record calls it `evidenceTrace`. The evaluator reads both shapes, and recomputes labels from the preserved contract when an older row has an `{available:false}` placeholder. This keeps offline rechecks useful without changing any Worker calls. A source decision missing for a cited claim makes its review contract incomplete. Do not interpret a reviewer `answered` label or a structurally complete report as a human quality score.

The repeated `quality-calibration` run is four questions with three attempts each (12 answers) and can take about 15 minutes. Keep new generalization checks out of that repeated set: the separate **Reading Companion live answer evaluation** workflow can run a single `holdout` case by selecting its `case_id`, with one attempt. A single fresh case adds only its own answer calls and does not lengthen the calibration run. Use the same rubric to score it, and do not add expected authors or titles as live retrieval instructions.

## Recheck a saved quality report without AI or network calls

The standalone `recheck-live-answer-evaluation.mjs` script reapplies the current structural audit to a saved quality JSON report. It does not contact the Worker, retrieve books, or call a model. First extract `reading-companion-live-answer-evaluation.json` from the GitHub Actions artifact ZIP, then run:

```powershell
node .\reading-companion\recheck-live-answer-evaluation.mjs `
  --input .\downloaded-artifact\reading-companion-live-answer-evaluation.json `
  --output .\downloaded-artifact\reading-companion-live-answer-evaluation.offline-rechecked.json
```

The new `offlineRecheck` fields preserve the original report and show the corrected structural score alongside it. Reviewer labels are also refreshed from saved traces when an older artifact lacks support-issue dispositions. `supportIssueDispositions` separates final-answer issues from claims rejected before the final answer, rejected alternate sources, and unresolved cases; the aggregate issue count remains available. This can correct evaluator false negatives and clarify review outcomes, but it does not change the generated answer or verify factual truth. Run its regression tests with `node --test .\reading-companion\live-answer-evaluation.test.mjs`.

The default `selected-books` run keeps the four one-book cases restricted to their selected work and uses curated fixed queries for all seven; the three comparison cases still search across books. It estimates 14 baseline answer/review inference calls, plus any conditional Worker repairs. The `all-books` option uses the live planner for each question and estimates 21 baseline calls (7 planner + 14 answer/review), plus conditional repairs and up to 7 conditional gap-planner calls. You can select one case to keep a diagnostic run smaller. Both choices require the live-AI confirmation. Review answer text and cited passages manually; the automated checks remain structural and do not establish semantic accuracy.
